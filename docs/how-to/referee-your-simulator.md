# Referee my simulator

**Goal:** catch queue and fill-logic bugs in a backtester or exchange simulator before they reach a strategy. The
referee replays the same orders with the exact FIFO engine and compares the fills order by order with your
simulator's fills.

Several bugs of this kind were reported in widely used engines: an unrelated cancel moving an order to the front of
the queue, queue ahead not capped when the displayed size shrank, two trades sharing one volume budget, fills decided
on the pre-trade book, a fill equal to the leaves quantity not completing the order. Each was found by hand. The
referee turns those classes, plus the rules from the [independent audit](../concepts/audit-rules.md), into small
fixtures you can run in CI.

**You need:** `pip install queuetruth`, and a way to run your simulator on a given dataset with a given list of
orders and to write out its fills.

## 1. Generate the bug-class fixtures

<!-- check-docs: run -->
```sh
queuetruth referee fixtures --out fx
ls fx
```

`fx/` holds one directory per bug class and a `MANIFEST.sha256`. Each class directory contains:

| File | Content |
|---|---|
| `dataset/` | a small synthetic order-level dataset: `manifest.json`, `instruments.parquet`, `data_quality.json`, `mbo/date=2026-06-15/instrument_id=1/part-00000.parquet` (`qt.mbo`) and `trades_source/...` |
| `schedule.parquet` | the orders to place (`qt.shadow_spec`, one order with `shadow_id` `x`) |
| `expected_results.parquet` | the exact engine's outcome for that order (`qt.shadow_results`) |
| `expected_fills.parquet` | the exact engine's fills (`qt.shadow_fills`, zero to three rows) |
| `README.txt` | one paragraph: the scenario, what the exact engine does and what a buggy simulator does |

Every class uses instrument id `1` on session date `2026-06-15`. The fixtures are generated by code
(`qt_testkit::bugclasses`); the same set is committed under `tests/fixtures/referee/`.

The 16 classes (directory names as written by `referee fixtures`):

| Directory | Venue | The simulator must... | Motivating report or ruling |
|---|---|---|---|
| `01_unrelated_delete_keeps_position` | CME | not move an order to the front when an order behind it at its level is deleted | NautilusTrader #4370 |
| `02_level_shrink_caps_queue` | CME | cap queue ahead when the displayed level shrinks below it (fills 5 when the queue depletes) | NautilusTrader #5016 |
| `03_distinct_trades_each_consume` | CME | let two distinct trades with the same price and timestamp each consume their own volume | NautilusTrader #5017 |
| `04_post_trade_book_decides` | CME | decide fills on the post-trade book: an aggressor's remainder resting at the order's price is taken as a cross | NautilusTrader #3596, audit ruling A5 |
| `05_partial_fills_sum_to_cum` | CME | report per-fill quantities that sum to the cumulative quantity (10, 15, 5 for 30) | hftbacktest #316 |
| `06_fill_equal_to_leaves_completes` | CME | complete an order when a fill equals its leaves quantity | hftbacktest #312 |
| `07_size_increase_loses_priority` | CME | send an order ahead to the back of the level when its size increases | |
| `08_price_change_loses_priority` | CME | send an order ahead to the back when it changes price and comes back | |
| `09_hidden_print_no_queue` | Nasdaq | not count a hidden-order print as consumption of the displayed queue | |
| `10_trade_through_fills` | CME | fill by trade-through when a sweep trades through the order's price | |
| `11_fill_before_cancel_effective_stands` | CME | keep a fill that happens after the cancel is sent but before it is effective (latency race) | |
| `12_hidden_execution_at_price_after_queue` | Nasdaq | fill on a hidden execution at the order's price once no displayed interest is ahead, and by trade-through on a hidden print through its price | audit ruling A3 |
| `13_execution_without_print` | Nasdaq | follow queue ahead from executions of the orders ahead, including executions with no print | audit ruling A4 |
| `14_off_price_print_not_trade_through` | Nasdaq | not treat an off-price print of an order ahead as a trade-through | audit ruling A4 |
| `15_cme_same_size_modify_loses_priority` | CME | send an order ahead to the back on a same-price, same-size modify (CME only) | audit ruling A6 |
| `16_crossed_at_live_takes_opposite` | CME | fill a marketable order as a taker against the displayed offers, one fill per price level, and rest the remainder | audit ruling A5 |

Read each `README.txt` for the exact numbers of each scenario. Classes 1 to 11 are the list in SPEC 5.8;
classes 12 to 16 come from the audit rulings. The exact engine reproduces every fixture's expected results and fills
(`o_ref_fixtures_exact_engine_matches_expected` in `crates/replay/tests/fixture_truth.rs`); the designed outcomes
are checked in `crates/testkit/tests/bugclasses.rs`.

Not every class applies to every simulator. An L2 simulator cannot see order-level priority, so classes 1, 7, 8, 13
and 15 test information it does not have; classes 9, 12, 13 and 14 matter only if you replay Nasdaq; class 11 matters
only if your simulator models latency. Run the classes that match your design, and use the tolerance flags
(section 3) only for classes where your model is approximate on purpose.

## 2. Run your simulator on each fixture

For each class directory, feed its `dataset/` to your simulator, place the orders in its `schedule.parquet` and write the fills
it produces.

The schedule is `qt.shadow_spec`: `shadow_id`, `instrument_id`, `side` (byte `B` or `A`), `price_mode`, `price`,
`offset_ticks`, `qty`, `ts_submit`, `latency_ns`, `ts_cancel`, `group`, `source`, `order_key`. Prices are integers
with the dataset's price exponent (`price_exp_by_instrument` in `dataset/manifest.json`, `-9` here, so
`5000000000000` is 5000.00). The dataset is plain Parquet: table `qt.mbo`, one row per order-level record in feed
order. See [Schemas](../reference/schemas.md) for every column.

If your simulator takes L2 data, synthesize it from the order-level data:

<!-- check-docs: run -->
```sh
D=fx/02_level_shrink_caps_queue/dataset
queuetruth replay --data "$D" --out l2-view --write-l2 --l2-depth 10 --bbo none --trajectory none
ls l2-view/l2/date=2026-06-15/instrument_id=1
queuetruth export l2-npz --data "$D" --instrument-id 1 --date 2026-06-15 --out l2.npz
```

`replay --write-l2` writes `qt.l2` Parquet under `l2-view/l2/`. `export l2-npz` writes one instrument-day as an
hftbacktest event file (`.npz` with one structured array, `data`). Both take `--l2-cadence-ns` and `--l2-trades`.

Write the simulator's fills in one of two forms. `--sim-fills` accepts either:

- **A fills table** (Parquet, or `.csv` with the same columns), one row per fill. Required columns: `shadow_id` and
  `fill_qty`. Optional: `ts_event` (or `ts`), the fill time in ns or as a timestamp; without it the first-fill time
  error is not computed and is not checked. Other `qt.shadow_fills` columns are ignored, and the file needs no
  `qt.schema` metadata. Float quantities (as in `qt.zoo_fills`) are rounded to the nearest integer. The simulator's
  filled quantity for an order is the sum of its `fill_qty`.
- **A canonical log directory** with `orders.parquet` and `events.parquet` (or `orders.csv` and `events.csv`), if
  your simulator already emits order events. Orders need `order_key`; events need `order_key`, `event_type`, and for
  `fill` events `qty`, `px` and a timestamp (`ts_exchange`, else `ts_local_recv`, else `ts_local_send`). `fill_id`,
  `ref_fill_id` (for `fill_bust` and `fill_correct`) and `source = "sim:<name>"` are used when present. An order
  matches a scheduled order by `shadow_id`, or by the schedule's `order_key` when that column is set. See
  [Import fills](import-live-logs.md) for the format.

## 3. Run the referee

First, referee the exact engine's own fills against itself. This must pass:

<!-- check-docs: run -->
```sh
C=fx/05_partial_fills_sum_to_cum
queuetruth referee run --data "$C/dataset" --schedule "$C/schedule.parquet" \
    --sim-fills "$C/expected_fills.parquet" --simulator exact@0.1.0 --out ref-ok
cat ref-ok/referee_report.json
```

Now make a deliberately wrong simulator output: drop the last fill, as a simulator that loses the final partial fill
would.

<!-- check-docs: run -->
```python
from pathlib import Path

import pyarrow.parquet as pq

fills = pq.read_table("fx/05_partial_fills_sum_to_cum/expected_fills.parquet")
print(fills.select(["shadow_id", "fill_seq", "fill_qty", "cum_qty", "reason"]).to_pylist())
wrong = fills.slice(0, fills.num_rows - 1).select(["shadow_id", "fill_qty", "ts_event"])
Path("mysim-out").mkdir(exist_ok=True)
pq.write_table(wrong, "mysim-out/fills.parquet")
```

The referee now fails the gate and exits with code 1:

<!-- check-docs: run exit=1 -->
```sh
C=fx/05_partial_fills_sum_to_cum
queuetruth referee run --data "$C/dataset" --schedule "$C/schedule.parquet" \
    --sim-fills mysim-out/fills.parquet --simulator mysim@1.4.0 --out ref-bad
```

The report is written even when the gate fails:

<!-- check-docs: run -->
```python
import json

r = json.load(open("ref-bad/referee_report.json"))
print(r["pass"], r["discordant"], r["qty_mismatch"], r["by_reason"])
print(json.dumps(r["examples"][0], indent=2))
assert r["pass"] is False and r["qty_mismatch"] == 1
```

The general form:

<!-- check-docs: skip (needs a simulator) -->
```sh
CLASS=07_size_increase_loses_priority   # any directory under fx/
queuetruth referee run --data "fx/$CLASS/dataset" --schedule "fx/$CLASS/schedule.parquet" \
    --sim-fills "mysim-out/$CLASS/fills.parquet" --simulator mysim@1.4.0 --out "ref/$CLASS"
```

| Flag | Meaning |
|---|---|
| `--data` | dataset directory (required) |
| `--schedule` | the simulator's orders as `qt.shadow_spec` (required) |
| `--sim-fills` | the simulator's fills: a fills table or a canonical log directory (required) |
| `--out` | output directory (required); the report is `<out>/referee_report.json` |
| `--simulator NAME[@VERSION]` | recorded in the report; default `unknown`, or the `sim:<name>` source of a canonical log |
| `--max-discordant N` | tolerated `sim_only + exact_only` (default 0) |
| `--max-qty-mismatch N` | tolerated quantity mismatches (default 0) |
| `--max-ttf-err-ns DURATION` | tolerated absolute first-fill time error, for example `0`, `250us`, `5ms` (default 0) |

`referee_report.json` is a `qt.referee_report` (`schema_version` 1):

| Field | Meaning |
|---|---|
| `spec` | the run's spec echo (dataset, schedule, sim_fills, simulator, tolerance) |
| `simulator` | `{name, version}` |
| `n_orders` | scheduled orders in the exact replay |
| `n_both_filled` | orders filled by both |
| `discordant.sim_only` | orders your simulator filled and the exact replay did not; fills for orders not in the schedule count here too (reason `unknown_order`) |
| `discordant.exact_only` | orders the exact replay filled and your simulator did not |
| `qty_mismatch` | orders filled by both with a different total filled quantity |
| `max_abs_ttf_err_ns` | largest absolute first-fill time error (simulator minus exact) over orders filled by both; `null` when not computable |
| `ttf_err_p50_ns` | median absolute first-fill time error, rounded to ns; `null` when not computable |
| `by_reason` | disagreeing orders counted by the exact `first_fill_reason` (`never` when the exact replay did not fill) |
| `tolerance` | the thresholds used |
| `pass` | `sim_only + exact_only <= max_discordant`, `qty_mismatch <= max_qty_mismatch` and `max_abs_ttf_err_ns <= max_abs_ttf_err_ns` |
| `examples` | up to 20 disagreeing orders: `order_key`, `exact` (`filled_qty`, `ts_first_fill`, `end_state`, `first_fill_reason`) and `sim` (`filled_qty`, `ts_first_fill`) |

Exit code 0 means `pass` is true, 1 means a tolerance was breached (`QT-GATE-001`), 2 means an error (the CLI exit
codes are tested by O-CLI-1). The counting rules above are tested on hand-built inputs in
`python/tests/score/test_score_referee.py`.

For any disagreeing order, `queuetruth why` prints every book event at the order's level with the exact queue
position after each (see [Explain one fill](explain-one-fill.md)):

<!-- check-docs: run -->
```sh
C=fx/05_partial_fills_sum_to_cum
queuetruth why --data "$C/dataset" --shadows "$C/schedule.parquet" --shadow-id x
```

## 4. Put it in CI

A sketch for GitHub Actions; replace the simulator step with your own command.

```yaml
# .github/workflows/referee.yml (sketch)
jobs:
  referee:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - run: pip install queuetruth==0.1.0 ./my-simulator
      - run: queuetruth referee fixtures --out fx
      - run: |
          status=0
          for c in fx/*/; do
            c=$(basename "$c")
            python -m mysim.run --data "fx/$c/dataset" --orders "fx/$c/schedule.parquet" --out "out/$c"
            queuetruth referee run --data "fx/$c/dataset" --schedule "fx/$c/schedule.parquet" \
                --sim-fills "out/$c/fills.parquet" --simulator "mysim@$GITHUB_SHA" --out "ref/$c" || status=1
          done
          exit $status
```

Pin the queuetruth version in CI: the fixtures are generated by code, and a new version may add classes.

## 5. Regression-test against real data

The fixtures are small and synthetic. To compare two versions of your simulator on real data, take an order-level
dataset you are licensed to use, sample a schedule, and referee both versions against the same exact replay:

<!-- check-docs: skip (needs user data) -->
```sh
queuetruth shadows sample --data my-ds --n 5000 --out sched.parquet
queuetruth referee run --data my-ds --schedule sched.parquet --sim-fills v1/fills.parquet --simulator mysim@1.3 --out ref-v1
queuetruth referee run --data my-ds --schedule sched.parquet --sim-fills v2/fills.parquet --simulator mysim@1.4 --out ref-v2
```

An L2 simulator will not match exactly on real data, so compare `ref-v1` and `ref-v2` rather than expecting `pass`
(both commands exit 1 when the default zero tolerance is breached). A change that moves `discordant` or
`qty_mismatch` when you meant to change something else is the signal. For a statistical view of the same comparison
(bias with confidence intervals, discordance tests by queue position), use
[`queuetruth score`](../reference/cli.md#queuetruth-score) with the exact arm and your simulator's log on the same
schedule (see [Score my Nautilus backtest](score-nautilus-vs-binance.md)).
