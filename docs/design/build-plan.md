# How queuetruth was built and verified

This page summarises how v0.1 was built: specification first, then code in gated phases, then independent checks.
The contract itself is the [design specification](spec.md); what each test checks is on
[How queuetruth is tested](../testing.md); the real-data numbers are on [Results](../RESULTS.md).

## Specification first

Before any code existed, the [design specification](spec.md) fixed every public name: crate and module APIs, Arrow
and JSON schemas, CLI flags, HTTP endpoints, error codes, the semantics of the book, shadows, queue models,
calibration, scorer and service, and an oracle list with hand-computed expected values (section 6). An independent
audit of that specification against primary sources (hftbacktest's source at the pinned commit, the ITCH 5.0
specification, the earlier prototype's venue notes) produced binding rulings that were folded into it before the
affected code was written; they are listed with their regression tests on
[Rules from the independent audit](../concepts/audit-rules.md).

## Phases and gates

The code was written largely by AI coding agents working in parallel against the specification. Each unit of work
owned a disjoint set of files, could not change a public name, schema or dependency on its own, and recorded any
deviation from the specification instead of changing the contract silently. A phase started only after the previous
phase's gate passed.

| Phase | Scope | Gate |
|---|---|---|
| Scaffold | workspace with every crate and dependency edge, pinned toolchain and dependencies, core types, JSON and Arrow schemas, golden values for the queue models, run identity | `make gate-0` |
| Foundation | book and replay, ingest (ITCH, DBN, CSV, crypto L3, Tardis L2), L2 view, test kit with naive reference implementations, statistics | `make gate-1` |
| Main build | queue-model zoo, calibration, features and learned model, live-log importers and scorer, referee, report, CLI, HTTP service, MCP server | `make gate-2` |
| Integration | end-to-end parity and determinism, real-data checks, benchmarks, docs, packaging | `make gate-3` |

`make gate-3` runs `make test` (lint, Rust, Python and service tests), the end-to-end tests, the real-data checks,
the benchmarks, the release check (sdist, wheel and a clean-venv smoke test), the examples, the docs checks and the
compose checks.

## Pins

- Rust 1.97.1 (`rust-toolchain.toml`), edition 2024, `#![forbid(unsafe_code)]` in every crate except the PyO3
  bindings, `clippy -D warnings`. Every crate dependency is pinned to an exact version.
- Python 3.11 or later for users; development uses a locked `uv` environment resolved with `exclude-newer`, so every
  resolved release was at least two weeks old when it was locked.
- hftbacktest is not a dependency. The optional cross-check against hftbacktest 2.4.4 runs in its own venv
  (`make hbt-crosscheck`).
- No market data in the repository or in tests. Fixtures are synthetic and generated by the project's own code;
  real-data runs write only to the gitignored `.realdata/` directory.

## Independent checks

- **Oracles written apart from the production code**: a naive reference book and shadow engine, a line-by-line
  transliteration of hftbacktest's queue code, an independent matching-engine oracle for the shadow fill rules, and
  statistical reference values generated with statsmodels, scipy, lifelines and R.
- **Reviews** of the Rust engine, the Python analytics, the trader-facing workflow and the service's security. Each
  security finding was reproduced, fixed and turned into a regression test (`service/tests/security/`).
- **Real data**: two public Nasdaq TotalView-ITCH days, compared with the earlier private prototype's outputs and
  with the feed's own execution prints ([Results](../RESULTS.md)).

These checks are independent of the production code, not of the project: they were done for the same author, not by
an outside firm.

## Definition of done for 0.1.0

The release is cut only when all of these hold:

1. `make gate-3` is green locally, and CI is green on macOS arm64 and Ubuntu.
2. Every oracle of the specification's section 6 passes (the optional hftbacktest cross-check and the compose smoke
   test may be skipped with their reason printed).
3. The real-data checks RD-1 to RD-7 match exactly and RD-11 passes; RD-8 to RD-12 are recorded with their numbers.
4. `make schemas` leaves no diff, and every option that changes an output is part of the run's spec and `run_id`.
5. The performance table is measured on a quiet machine, with every missed target listed.
6. Outputs are byte-identical across runs and thread counts.
7. The wheel and sdist pass the release check; the service tests pass on an ephemeral PostgreSQL 16; the MCP server
   serves results locally.
8. The README status table matches the evidence, and no market data is in the tree.

Where these stand is tracked in `CHANGELOG.md` at the repository root and on [Results](../RESULTS.md). Performance (item 5) has so far been measured only on a loaded machine.
